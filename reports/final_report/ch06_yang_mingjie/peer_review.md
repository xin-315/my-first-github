# Peer review of quality claims and requirement alignment

Reviewed by the testing contributor against the existing source snapshots on 29 October 2026. These are written review findings, not messages sent to teammates.

1. **High: Offline packaging claim exceeds the implementation.** Original Ch4.6 says no demonstration dependency is external; current Ch4 likewise claims complete offline execution. Existing index.html references a remote ECharts script. Fresh external-blocked browser load raises `echarts is not defined`. Bundle the vendor dependency or narrow the claim and repeat the browser acceptance check.
2. **High: Authentication description does not match auth_service.py.** Current Ch4 AD-5 describes salted hashing and cryptographic tokens. The inspected service ignores the password and builds a predictable timestamp string. No verification or logout routes exist. Treat it as demonstration identity handling until implementation changes are reviewed.
3. **High: Telemetry and provenance claims are unsupported.** Current Ch4 claims mutable attempt aggregation and reset. The existing report service returns fixed counts and scores; the reset route is absent. A wrong answer did not change 18 attempts or 14 correct answers. Correct the data_source claim and the affected Ch2/Ch6/Ch7 conclusions.
4. **Medium: Strict error contracts differ from fallback behaviour.** Current Ch2/Ch4 require unknown IDs to return 404 and invalid options to return 422. Existing service/tests deliberately accept 200 fallback. Agree on one contract before claiming acceptance.
5. **Medium: Baseline quantities are stale.** The tested ae7ab47 software has 17 backend questions, nine subject codes, nine API operations, ten test modules, 99 functions and 183 cases. Older comparison commit 10f2065 has 12 questions and 150 cases. Latest master 7d29bad retains the tested API, frontend and tests, with a launcher-only source change. Replace unqualified 12/36/8/145/147 claims with quantities tied to the selected snapshot.
6. **Medium: Requirement definitions changed.** R10 and the excluded R12 to R14 differ between the task pack and current Ch2. Functional Table 2.2 became Table 2.1, while the NFR IDs changed. Use requirement_crosswalk.md to agree a common baseline; do not silently renumber Ch6 evidence.
7. **Medium: Performance evidence must identify its method.** The original empirical test file is not a per-operation P95 harness. Supplementary loopback timings are real but cannot substantiate a separately claimed 1,000-call in-process experiment, controlled cold-start figure or cloud-mode latency.
8. **High: Security review must address existing credential configuration.** Hardcoded configuration is present in the frontend and research material. No values are included in this review. The responsible maintainer needs to remove exposed configuration and arrange rotation. Passing input tests does not satisfy a zero-secret acceptance criterion.
9. **Medium: RAGAS and MMLU claims require narrower wording.** The existing evaluator does not compute the four RAGAS metrics. The aggregate MMLU file lacks per-item counts and paired observations; the available engine caps inputs at 200 rows per source. Retain all negative results and avoid significance or 4,445-evaluated-item claims.
10. **Medium: Ch6.5 must distinguish regression success from acceptance.** All original tests pass under their implemented assertions; several formal acceptance criteria are unmet or unverified. The revised achievement table records that distinction across all 14 requirements and both NFR baselines.

The current Cycle 3 Ch4 numbering differs from the original allocation: its section 4.6 is now the ADR matrix. This review therefore covers both the originally assigned non-functional design material and the current equivalent claims.
